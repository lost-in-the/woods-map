# Woods Map

Rails Engine that mounts a code-comprehension web explorer over a published
[Woods](https://github.com/lost-in-the/woods) index. Developers read a unit's
code as Rails runs it, follow references, data passages and lifecycles, see
relationship graphs, schema and history, and get change-impact reports with
sharable focus URLs. It reads the published index only: no live database, no
runtime reflection, no git subprocess at request time.

Status: M1 Reading, M2 Passage, M3 Diagrams, M4 History, M4b Impact (the map side; Woods owns `woods:impact` output), M5 Graph, M6 Trail and M8 Staging are closed, and their pages landed (M5: neighbourhood endpoint, Graph tab and full-screen page in the butterfly layout of D-30, flow overlay and commit timeline). M7 Guide has landed, off by default, and stays open on a real-provider run. The design study, decision log, boards
and milestone plan live in `docs/design/` and are the source of truth for
scope; `docs/design/foundations/tokens.css` is the stylesheet the engine ships
verbatim (a spec keeps the two copies identical).

## Commands

```bash
bin/setup                    # bundle install (woods comes from a sibling checkout or git)
bin/rake spec                # unit and request specs against spec/dummy
bin/rubocop -a               # lint + autofix
```

Integration validation happens in a host application from
[`lost-in-the/woods-testbed`](https://github.com/lost-in-the/woods-testbed):
mount the engine in a variant, run `woods:extract`, open `/woods`.

## Non-negotiables

- **Floors match Woods**: railties >= 6.0, Ruby >= 3.0. Only the RubyLLM guide needs Ruby 3.2 and it degrades to a notice below that.
- **No build step, no asset-pipeline dependency**: every JavaScript library is vendored under `vendor/javascript/`, served by the engine's own assets route under one content digest for the whole set (so relative URLs between files work), and pinned by a literal `<script type="importmap">` in the layout. No importmap-rails, no turbo-rails, no Node.
- **One token sheet**: `tokens.css` is the design's file and ships verbatim (a spec compares the two copies); engine-only rules go in `map.css`; views never hard-code a colour or a size and compose from the partials under `app/views/woods_map/shared/` and `components/`. Every page must pass axe (colour contrast, names) at 1440, 960, 640 and 390.
- **Engine only**: there is no standalone launcher. The map belongs inside a Rails application, like Woods.
- **Index only**: every read goes through `Woods::PublishedIndex` or `Woods::MCP::IndexReader` pinned to one generation per request. Never resolve a payload path yourself; never read `manifest.json` from the index root.
- **Read-only and gated**: loopback without a token boots with a warning; anything else refuses without `WOODS_MAP_TOKEN`; `config.authorize` lets the host add its own gate. Unit routes take typed identifiers. File routes admit only exact permitted `file_map` keys; never resolve those keys on the host filesystem.
- **Mounting is explicit**: `mount WoodsMap::Engine => "/woods"`; the Railtie injects nothing.

## Gotchas

- A horizontally scrolling wrapper (`.tblwrap`, `pre.cmd`, `.cvwrap`, `.tl`) is rendered with `role="region"`, an `aria-label` and `tabindex="0"` so it is reachable without JavaScript; the `cliff` controller removes the tab stop when nothing overflows. A new scroll wrapper must do the same.
- `Woods::MCP::IndexReader#search` answers with symbol keys and rows of identifier, type and match_field only; `Repository#search` stringifies the keys and adds `file_path` from the graph nodes. Read search results through the repository.
- Freshness is `Woods::SourceInputs::Status` over the index root (`PublishedIndex#index_dir`), never the payload dir; a quick check that finds no changes can still say `unknown` when Woods could not verify the boot boundary, and the bar reports Woods' reasons rather than upgrading the verdict.
- Unit identifiers and file keys keep their extension in the URL. Their routes declare `format: false`, yet Rails reads a format from the path extension when a request has no Accept header (curl, crawlers) or a browser's catch-all one (`.yml` → YAML, a 500; `.js` → a page without the layout). `WoodsMap::PathExtension` makes those pages HTML; a new route that takes a path-like value must stay `format: false` and HTML.
- Routing drops a trailing slash and squeezes a doubled one, so an identifier ending in `/` (every app's root route, `GET /`) arrives without it. `WoodsMap::RoutedIdentifier` tries the slashed identifier when the raw path shows the slash; read unit identifiers from the route through it, never `params[:identifier]` alone.
- Dependency targets can name what the index never extracted (framework classes, engine controllers, unmigrated tables) or a type it does not publish (`framework`; `view` and mistyped test coverage before woods#819). `unit_link` links a typed identifier only when the pinned generation holds it, so newer data links on its own and older generations keep the text; pass `listed: true` only for units taken from the generation's own listing.
- The Code tab's count is Woods' `metadata.loc` (lines neither blank nor a comment), labelled `loc`; the code header names the file's full line count beside it. Never call one by the other's name.
- File navigation uses stable ownership pages through `Repository#file_owners`, matching both `file_path` and `source_paths` across primary nodes and variants. File pages never reconstruct source. `file_owner` is retained for existing source-line links only. A bare identifier alone cannot choose the correct unit type for a file. File-tree caches include the index identity and pinned generation.
- `Neighbourhood` receives the selected unit type from its route and traverses typed identities, including variant edges. Type filters apply to the endpoint first reached by each breadth-first edge visit; missing type metadata on older graphs falls back to the primary node. Graph-analysis notes retain their published identifier-level scope.
- `Lifecycle` keeps only callbacks whose method the unit's source or an inlined concern defines; framework callbacks and procs are counted as a limit, not drawn as steps. `?view=` picks the sequence (default), flowchart or lanes (`swimlane-beta`) text from the same steps. State diagrams come only from published `state_machine` units reached by a reverse `state_machine` edge (`StateMachineView.for_model`); structured transition callbacks (`metadata.transition_callbacks`, woods#796) sit on the transitions their literal scope admits (`StateMachineView#callbacks_for`, before/around/after columns and the diagram's edge labels); a callback whose scope is not literal is listed apart; a generation without them keeps its raw DSL lines, never parsed.
- `Outline`, `SchemaView` and `Neighbourhood` read the generation at construction, so a view may use them after the repository block closes. `HistoryView` and `HistoryTimeline` read lazily and are rendered inside the repository block.
- History reads only `Repository#git_commits` (`PublishedIndex#git_commits`, Woods W-3); absence (`commit_table_state` :absent, :unreadable, :unsupported) falls back to `metadata.git` and is named as a limit, never treated as "no commits". The *gen* column and *generations touching* come from `CommitLedger`, which compares the sha lists of retained generations' tables (`Repository#with_generation`), never code. Heat is per file (`PathHeat`); the unit diff is Woods' report record (`UnitDiff` over `ImpactRange`) plus Woods' unified source diff (`SourceDiff` over `Woods::Impact::UnitDiff`, woods#802), never a map-side diff. Line counts and hunks are the table's own (woods#804, `CommitRows::FileChange`); a hunk links into the Code view only when the commit is the file's latest touch, since older hunks are in their commit's coordinates. *Facets moved* is `GenerationFacets`: one `SourceDiff` per consecutive retained-generation pair, cached per index identity; *by generation* is `GenerationStrip` over the ledger. `?span=first..last` (`DateSpan`, inclusive UTC days) narrows the History tab and `/woods/history`; the `brush` controller builds it from a drag or Shift+arrows and Enter, and a click without a drag keeps the bar's link. `SourceDiff.backend` is nil on a Woods without the unit diff: the column is then left out and the diffs say so, and specs stub it. See `docs/design/notes/history.md`.
- `Passage` takes filter applicability from Woods' resolved chain (W-8, woods#758): each filter's `applies_to`, `owner` and `applicability`, in published chain order. A `conditional` filter (an `if`/`unless` Woods does not evaluate) is marked as such and its ✓ means it can run, never that it does. On a generation without those keys (`Passage#resolved?` false) it falls back to the declared `only`/`except` and names the resolved chain as a limit; the map never resolves the chain itself. Assigns, params and renders come only from Woods' `metadata.action_facts` (W-7, `WoodsMap::ActionFacts`); without them it ties templates to actions through the `view_render` edge or a mailer's template list and raises no flag. Admitted actions missing facts, absent template ivar metadata, partial chains beyond the traversal limit, dynamic render targets (W-7 renders keyed `object`) and a template's `metadata.unresolved_partials` stay incomplete and are named (`PassageTemplates#unresolved`); format, `head` and redirect responses are complete. Template ivars are lexical mentions: unmatched mentions are advisory, with no claim about a runtime value. Shared partial focus follows reverse render edges to find its owners. A fact the index lacks is named as a limit, not derived; the map never parses host source.
- `RoutesView` (the controller Routes tab) lists the controller's `metadata.routes` joined by `VERB path` to route units, plus `route_dispatch` route units the metadata omits. Helpers are `<name>_path`/`<name>_url` of the published route name. Findings come only from graph analysis's `unresolvable_routes` for that controller, shown as notes (woods#726 tracks implicit-render false positives). `route_file` nodes carry no source, so the `routes.rb` line is text, never a link. Navigation edges name the controller only; the helpers each referencing unit calls and their actions come from that unit's `metadata.route_helper_references` (woods#795), matched by controller and `via`; a unit without the key (an older generation) shows *not in this generation* and keeps the woods#795 limit.
- `?author=` (woods-map#92) is matched exactly against the commit table's `author`, as git recorded it; it is index data, never free text, and anything but one string up to 256 characters is no filter (`AuthorFilter#author_param`). `HistoryView#people` and the timelines' `authors` read the unfiltered window, so the filter never hides the other authors. Without a commit table the History tab filters only the five `metadata.git` commits and offers no neighbourhood link.
- The impact page computes nothing a range needs: `BlastRadius` propagates over `reverse_via` of one generation and `ImpactReview` runs only the rules that generation can answer, listing the rest with what they need (W-7, W-8, a range). A range delegates to `Woods::Impact::Report.compare` (W-12, decision D-1), optionally loaded from `woods/impact/report`; a saved report (`/woods/impacts/:id`, E-6) is read through `Woods::Impact::Store#read`, never a path the map builds. `RangeReport` turns either into the Overview, Changed, Risks, Flows, Tests, Graph and Unknown tabs from the string-keyed schema version 1 evidence without deriving another diff or traversal. A record links only when its generation is the pinned one and the generation has the typed unit; other identities stay text with their generation. Missing capability, unreadable evidence and missing saved reports are explicit states. Manifest checksums cover manifests only; source sizes are not changed-line counts; the Changed tab's *lines* column reads the report's `source_changes` and only a focused row opens Woods' unified diff (`changed_diff`). Never render, offer or hand through Markdown or JSON reports (D-25).
- Flows and pins come only from Woods' published-index readers (woods#805), feature-detected so the map runs against a Woods without them: `Repository#flow_entry_points`/`#flow_document` (W-13) and `Repository#retention` (W-11, read from the index root). `flows_state` keeps `:absent` (no inverse published), `:unreadable` (Woods refused an artifact) and `:unsupported` apart from an empty answer; only `:available` gets a tab count. Steps are drawn only from the pinned generation's flow document; a range flow of another generation keeps its route and changed units without steps. Untargeted calls are counted, never drawn (their method strings can carry gem paths). Unknown pin state is never shown as "none".
- `?since=` (E-8) is `SinceParam#current_since`: one `ImpactRange` from the selector to now per request, read by `WoodsMap::Since`. Pages mark only what the report's records say: changed lines from the record's `source_changes` (`Since#line_marks`, only when the report's `now` is the pinned generation, since the ranges address that source), marginal notes on a changed line or by the metadata key they read (`Marginalia::Note#area`), files owning a changed unit in the tree, changed templates on the Passage, changed tables on the ERD, the report's emphasis on the Graph canvas (distance 0 is changed), on History and `/woods/history` the commits a newer retained table first carried (`since_commit?`, never a baseline commit), and Lifecycle steps whose method extent (`metadata.methods`) or callback `declaration` (woods#817) holds a changed line (`Since#changed_members`; flowchart and lanes add `class sN chg`, the sequence cannot), Passage filter rows by their W-8 entry's `declaration` (woods#820), and ERD and Schema columns from the record's `column_changes` (`Since#column_marks`, woods#821; ER attributes get a comment, removed columns are listed). Never compare payloads in the map.
- The guide (M7) never makes RubyLLM a dependency: only `WoodsMap::Guide.backend` requires `ruby_llm` and `woods_map/guide/agent`, and only when `guide_enabled` is set on Ruby 3.2+. Everything else (runner, store, answer) works with any chat that has RubyLLM's step-wise surface; specs use `FakeGuideChat` (`config.guide_chat_factory`), and `spec/woods_map/guide_agent_spec.rb` runs the real agent against an in-process fake provider and the real `woods-mcp`. The model sees `Guide::TOOLS` only. Context is rebuilt server-side from the pinned generation; answers link only identifiers in `Repository#identifier_index`. Streams run in `GuideStreamsController` (`ActionController::Live`) without holding the manifest lock; the answer's links are rendered from a fresh `Repository.open` when it ends. A turn streams once (`Store#claim`). While an answer runs, `Guide::Heartbeat` writes an SSE comment after `guide_heartbeat_seconds` of quiet, under the stream's write lock; never write to the stream outside `write_event` or that lock. Index MCP servers come from `Guide::ServerPool`, keyed by transport and `Repository#generation_key`: only a `done` or `limited` answer hands its server back (`Session#close(reuse:)`), anything else stops it; never share one server between two answers at once. Graph units reach the guide as `context[nodes][]` of `type:identifier` from the graph controller's `woods-map:graph-pick` event, and the server keeps only typed units of the pinned generation. *Draft an issue* is an answer action whose text is copied, never posted; it is the guide's own answer, not a Woods report (D-25). *Pin* and *open as investigation* are Trail board links (`Guide::Handoff`) built from the units the answer links (`Answer#cited`) and the turn's context; the board stays its URL.
- `PermittedAttributes` matches permitted keys against published model facts (columns, associations, collection `_ids`, attachments, rich text, class-body writers, then `attribute_writers`). With `attribute_writers` (woods#797) an unmatched key is an advisory flag, raised only on actions whose W-7 params read that method; without it the key stays unverified. `PartialLocals` flags a local passed (template `partial_renders`, or the action's own W-7 partial render) and missing from the partial's lexical `locals_read` (woods#798); a render whose partial is missing, publishes no reads (Haml, Jbuilder) or is dynamic is named as unchecked, never flagged. See `docs/design/notes/passage-mismatch-limits.md`.
- Every engine response carries the engine's Content-Security-Policy (`WoodsMap::ContentSecurityPolicy`, M8): scripts, styles and fonts only from `<mount>/assets/<digest>/`, inline scripts only with `content_security_policy_nonce`, no `'unsafe-inline'`. Views and helpers never write a `style` attribute (a spec greps for it): add a class to `map.css`; varying geometry takes a bounded class (tree `data-level`, step `data-depth`, `TABLE_MIN_WIDTHS`) or a presentational hint (`<th width>`). Pele's SVG styles go through the diagram controller's CSSOM `sanitize` hook; text Pele refuses is caught by `parse` before mount. `config.content_security_policy` amends (callable) or hands the header back to the host (`false`).
- Search with the palette, graph JSON, impact and the `.mmd` text routes (plain-text 429) are counted against `config.rate_limit` per `rate_limit_key` (`woods_map_rate_limit`, not Rails 7.2's `rate_limit`); the 429 is the 403 panel's plain page, served before the repository opens. The token-less loopback mode also requires a loopback `Host` (`Woods::MCP::OriginPolicy`, DNS rebinding) or a host in `config.allowed_origins`; request specs default to `host! 'localhost'`. Writes check Origin, then Referer, then Sec-Fetch-Site. `WOODS_MAP_RUN_HTTP_SERVER=1` runs the gate under Puma.
- Diagrams are drawn in the browser by Pele (D-21) from the Mermaid text the page carries; Ruby builds the text (`#mermaid` on the view objects, never inline in a view) and the panel keeps it as the fallback. Pass `mermaid:` and `label:` to the diagram partial, and `refusal:` when the type's budget (R-4) is exceeded: `Neighbourhood::NODE_BUDGET`, `SchemaView::TABLE_BUDGET`, `Lifecycle::SEQUENCE_BUDGET`, `Lifecycle::FLOWCHART_BUDGET` (flowchart and lanes), `StateMachineView::STATE_BUDGET`. A runtime refusal by Pele shows in the panel's status line, never only in the console. Every Mermaid panel renders its own ⎘ copy and ⤓ `.mmd` link (`components/_mermaid_tools`, `WoodsMap::MermaidExport`). Pass `name:` and `mermaid_url:`, and never add a copy tool of your own. The `.mmd` routes (D-25, [note](docs/design/notes/mermaid-text-urls.md)) answer the same text as `text/plain` through `MermaidText#render_mermaid`. Only a route default (`mmd: '1'`) makes a request `.mmd`, never a query parameter. The routes sit ahead of the glob routes, behind the same gate, and never exchange a URL token. A refused diagram is 422 with the reason, never truncated; build refusals with the view object's `#refusal`. Structurizr DSL and LikeC4 exports need W-9 and are not built. `spec/diagrams/pele_render_spec.rb` draws every generated text with the vendored build in Node: a text Pele refuses fails there, not on a page. `spec/diagrams/github_mermaid_spec.rb` parses the same texts (`spec/support/generated_diagrams.rb`; add a new diagram there) with the Mermaid GitHub renders (`MermaidExport::GITHUB_MERMAID_VERSION`, 11.16.1, vendored under `spec/vendor/github_mermaid` for the spec only): a text GitHub would refuse fails there, not in a reviewer's comment. Every `.mmd` route has a `.md` twin (route default `md: '1'` beside `mmd: '1'`, so every `.mmd` rule applies) answering `PrComment.build` as `text/markdown`; a comment over GitHub's 65,536 characters is 422, never cut. Absolute links start at `PublicUrl.base(request)` (`public_base_url`/`public_url_for` in views, `config.public_url` when set), never `request.base_url`.
- `DynamicView` (C4 dynamic, B-23) is offered only when `Landscape#attributed?` (W-9); its container names and technologies come from `Landscape`, never re-derived. `Repository#flow_failures` reads W-14's best-effort flow failures through `IndexReader#flow_failures` (empty on a Woods without it); Passage and Impact Flows name them, never derive a flow.
- `/woods/erd` (`Erd`) reads only `database_table` units and the model units that map them. Chunks group tables by database and model namespace (or by database) and are cut along relations at `SchemaView::TABLE_BUDGET`. A relation whose other end lies in another chunk is listed, never drawn. The route takes a chunk number, and `by` and `columns` are closed choices. Chunk numbers belong to one generation. `spec/support/large_schema_index.rb` generates the 300-model index in a temporary directory; do not check one in. The global bar comes from `ApplicationController#primary_nav`.
- Hover cards (B-3) are rendered with the Code tab as inert `<template data-card-target="card" data-href=…>` elements, one per linked unit (`CodeView#linked_targets`), and handed to the one tooltip as `data-tip-html` with `data-tip-delay="100"`. Hovering makes no request. Card markup must stay free of `abbr`, `[title]` and ⓘ, because the tooltip would open a nested tip.
- Reading settings (B-15) live in `localStorage["woods_map.settings"]` behind `try/catch`; the lens stays on its `?lens=` cookie. Wrap is an opt-in (`data-code-wrap=on` on `.wm`) that fits the source column to the one scroll region, never an automatic narrow-width wrap. *In editor at L…* is rendered hidden on the Code tab and shown only when this browser's editor template resolves; never build an editor URL from the index alone, and refuse `javascript:`/`data:`/`vbscript:` templates.
- The Share menu (`shared/_share`, E-6) is a `<details>` disclosure with the page's `focus_url`, which never carries `token`, and, from each `components/mermaid_tools` copy tool (`data-mermaid-name`, `data-mermaid-href`), the page's Mermaid text, its absolute `.mmd` URL and its pull-request comment (`data-pr-comment`, or the reason as `data-pr-comment-refusal`; [note](docs/design/notes/pr-comment-share.md)). It offers no Markdown or JSON report, not even Woods output handed through (D-25); the PR comment is the diagram in a fence and one line of links, nothing derived. The `y` key skips copy tools inside `.share`.
- The Graph tab's canvas (`graph` controller) fetches `/woods/graph/neighbourhood` for the page's own query and draws it with the vendored Cytoscape; the Pele flowchart and the list stay the no-JavaScript page and the Mermaid export. One layout, the controller's butterfly (D-30, woods-map#63): no layout library or extension is vendored, and radial and clusters layouts are gone. `routes` labels the edges between two units once (`×n`, `+k`), bundles a hub's taxi edges at a trunk outside its column (taxi-turn in px from the hub, negative from the target; never inside the column's span) and leaves labels whose both ends are shared to the lit state; end labels take no text backing, so they sit above the line. The focus stands alone in its column and `view` centres it unless a one-sided graph would lose more than a quarter of the zoom. Type tints are `--g` on `[data-gtype]` in `map.css`, read through a probe and mixed into `--panel`, so canvas and legend agree; a theme switch repaints. List rows carry `data-edge` (`GraphElements.edge_id`), the JSON's edge id. `spec/woods_map_graph_browser_spec.rb` times a 300-unit draw synchronously before load (virtual time freezes `performance.now()` once a timer fires); set `WOODS_MAP_GRAPH_BUDGET_MS` to enforce a budget. The tab and `/woods/graph` share `graphs/_explorer`; dragged positions are kept in `localStorage` per generation and query (A-3), and the page's blast tint comes from `BlastRadius`, never from the client. Domain clusters (woods#799) are drawn on Landscape only; never derive them from namespaces. Overview mode (fitted zoom below 0.5, where Cytoscape drops names, or more than 120 units or 150 edges) draws units unnamed and edges without arrows, dashes or labels until zoom 0.5; the count case also uses lighter renderer settings. `warm` draws a small graph off screen while the request is in flight.
- The Landscape reads containers only from graph nodes' `container` (W-9) and technologies from the BehavioralProfile unit; people and the system's name are host configuration (`landscape_actors`, `system_name`), never guessed. Edges leaving a database are not drawn as relationships (the index does not say which process runs a model's callback). `/woods/landscape.{mmd,dsl,c4}` are plain text (D-25); 422 without W-9. Components group only by published facts (graph node `package`, `namespace`, `domain_clusters`); `/woods/landscape/{context,components,quadrant,sankey,treemap}.mmd` answer 422 with the reason when the generation lacks them. Context people come only from `landscape_actors` and external systems only from what Containers draws; the map keeps no gem-to-service table (woods#814). Code sizes read `package_sizes` (woods#810), or sum node `loc` per distinct file without packages. Quadrant points stay in 0.02..0.98 with two decimals (Pele's lexer refuses `1.000`).
- The graph's flow overlay reads only `Repository#flow_entry_points`/`#flow_document` (W-13; `flow_state` is :unsupported on a Woods without the readers). A controller step names its action; it is drawn as the controller. Moves are matched to drawn edges in either direction, and anything else goes in the side list, never onto the canvas. The timeline matches commits to drawn units by graph node `file_path` and `source_paths` only.
- The code view is one scroll region (`.cvwrap`, D-24, woods-map#29): the source column grows to its longest line and the gutters are sticky. Do not reintroduce `overflow-x:auto` on `.src`.
- Code links consume only published `metadata.references` (W-1), resolved by exact target and target type in the pinned generation. `References` admits:
  - kinds `constant`, `association`, `callback_method` and `scope`, with confidence `verified` or `static`; a static link is marked dashed;
  - `ambiguous` spans, which become a popover button listing every published candidate (`_disambiguation`, the `disambiguation` controller); the map never picks one;
  - a span's `method` (W-6), which links to the method's line through the target's `metadata.methods` (W-2, `MethodLine`), or to the concern that owns it;
  - a self-reference only with such a line.

  `Callers` indexes the generation's verified and static constant spans by typed target and method, cached per generation. It feeds the callers panel, the margin's "called from" on a definition line and the outline's caller counts. An empty callers list proves nothing. The outline groups methods by owner from `metadata.methods` when the index has it. Their 1-based lines address annotated `source_code`; columns and lengths count UTF-8 bytes, including original newlines. Only unchanged file rows can carry links. Missing/invalid metadata and hidden or transformed rows stay unlinked; the internal reference cache is not a public link source. `source_line_map` runs contain annotated start, original start and length, not an ending line. Verification describes the published typed-registry evidence, not complete runtime call coverage.

- `Repository` reads through a `GenerationSnapshot` keyed by `generation_key`: the reader, the graph and the values built from them (`nodes_by_identifier`, `file_map`, file owners, `identifier_index`, `unit_listing`, `units(type:)`) are computed once per generation, shared across requests and deeply frozen; never mutate them. Build a new per-generation value with `snapshot.fetch(:name) { ... }` inside the request's pin. Specs that stub `graph` on a repository built from a double use `synthetic_published_index`.
- Long lists page through `ListPage` and `components/_pager` (`?page=`), and Mermaid text over `MermaidExport::INLINE_BYTES` is not carried in a page: a refused panel says so and offers no copy (its `.mmd` is 422), an unbudgeted one copies from its `.mmd` route. A new list that can grow with the application needs a page size.

## Conventions

- `frozen_string_literal: true` on every file; YARD on every public method and class.
- RuboCop with the same posture as Woods (`NewCops: enable`, target Ruby 3.0).
- Always `rescue StandardError`, never bare `rescue`.
- JSON output uses string keys, snake_case.
- Specs: unit specs with mocks plus request specs against `spec/dummy`; anything that needs a real index uses the fixture under `spec/fixtures/index/` (a minimal published generation) or a testbed variant.

## Work tracking

GitHub issues own active work and acceptance criteria. Every milestone and
requirement in `docs/design/plan.md` maps to an issue on the
[Woods Development project](https://github.com/orgs/lost-in-the/projects/1/views/1).
Rules:

1. Before opening a milestone issue, run the audit checklist in `plan.md` and name the requirement identifiers (FR, NFR, A, B, C, E, W) the issue covers.
2. When an issue is created, closed or re-scoped, update the matching row and the issue-links section of `plan.md` in the same pull request.
3. Record decisions in issues labelled `needs-decision`, then copy the settled decision into `docs/design/decisions.md` with the issue link.
4. Do not create a local task queue or copy issue status into a file; `plan.md` is a map, not a status board.
5. Data the map needs from extraction is a Woods issue (W-item), not a workaround in this gem.
